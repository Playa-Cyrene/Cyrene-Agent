# QQ 独立模块首次配置

此路径不要求任何旧 QQ 聊天历史，也不伪造已启用的旧 QQ 配置或在线身份来调用迁移流程。它是受信主进程的首次配置事务，尚未开放产品 IPC/UI，也不改变生产发行信任策略。

## 主机组合契约

- QqFirstSetupCoordinator 接收主机所有的 QqRuntimeConfig、已安装候选 ID、受保护凭据读取端口和实际模块工厂。只有数字 loopback 地址受支持。
- readConfiguration() 只提供非秘密配置；预览快照包含用户需确认的账号。确认前后重新检查配置、候选签名/选择、系统安全存储。
- readCredential() 只在明确确认后调用。主机必须从已授权的安全存储读取，拒绝明文/混淆回退。此事务不负责导入或保存新凭据，也不把秘密写入状态文件。
- 工厂必须快照传入配置/凭据，使用受信包解析与真实 utilityProcess。协调器在调用完成后清空自己的临时凭据字段；不能以共享可变对象作为未来重启配置。
- 主机先用独占 QQ 路由的 prepareFirstSetup(verifyStopped) 撤销旧路由并验证旧进程已不存在，再允许一次 attachModule(manager)。工厂创建后先 attach 尚未启动的 manager；协调器随后隔离 stage。
- verifyNoLegacyDriver() 在持久化准备之后、创建模块之前和选择之前复核。后两次应组合 router.isLegacyBlocked() 与可信进程停止证明，不能重复 prepare 并撤销已绑定模块。仅 adapter.stop()、空选择文件或 isLegacyBlocked() 都不是进程已消失的证明。
- 路由在整个事务期间不得并发恢复旧驱动。这是主机组合必须保证的独占性，不是三次“进程不存在”查询能独立保证的。

## 事务与恢复

QqFirstSetupStore 使用主机专用目录，原设置、聊天、绑定文件完全不修改。read() 返回：

- null：此存储没有持久化首次配置记录；
- prepared：已记录意图，尚不能证明模块启动情况；
- module-staged：曾观测到匹配账号的隔离模块；
- selected：持久化模块选择，不代表当前有活跃进程；
- rolled-back：已回退选择，不授权自动启动旧驱动。

全部记录只包含配置、包 ID、事务 ID 和阶段，不含 token 或 token 摘要。启动门控应把任何已存在记录视为需要主机明确恢复判断，不可凭 selected 自动执行模块，也不可凭 rolled-back 自动启动旧 QQ。陈旧锁不自动删除。

确认流程：重新校验 → prepared（先于路由撤权）→ 旧驱动不存在证明 → 读取安全凭据 → 再确认旧驱动不存在 → 隔离启动 → 真实 backend 身份一致 → module-staged → 重验 → selected → 激活 → 再确认活跃代。

取消仅适用于尚未确认的预览；确认启动后拒绝取消或重复确认。失败尽量停止新模块并持久化回退；无法确认停止或写盘失败时返回 recovery-required。显式恢复要求可信的全部 QQ 驱动停止证明，不重启任何驱动、不重放消息、不恢复秘密材料。

## 验证范围

测试使用真实文件存储和真实 QqModuleManager 配合合成 IPC peer，覆盖无历史首次配置、预览零副作用、取消、账号确认、配置/信任/安全存储变化、旧驱动运行或未知、隔离入站、真实身份不匹配、全部持久化检查点失败、恢复、重复调用、陈旧锁、损坏状态及路径符号链接。

它不能替代 Windows 安全存储/文件系统、安装器及真实 NapCat/QQ 验收。需要新凭据录入时仍须专门的主机安全保存工作流及用户授权，不能把本测试端口当作可从 renderer 任意注入的凭据 API。
