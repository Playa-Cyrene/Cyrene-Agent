# 正式回答实时预览：设计与施工方案

## 目标与范围

工作、学习、代码模式及启用工具的聊天模式，模型正文生成时立即显示在回答区；这一轮结束后，有工具调用则归入过程区，没有工具调用且运行成功则原地成为正式回答。模型推理内容继续实时显示在过程区。无工具聊天模式维持现有真正的增量显示。

“正在生成”的文字只是临时预览，不代表运行已成功，也不进入正式回答、语音播报或持久化正文。取消、错误、重试和用户交互不得把临时文字误提交为最终答复。

本次只改变桌面聊天界面的可见性与归类。工具执行、模型上下文、最终提交判定、会话存储格式和外部频道消息的语义不变。

## 已有能力与复用决定

| 已有能力 | 本方案如何复用 | 成本与限制 |
| --- | --- | --- |
| `streamChatWithSdk` 与 `UnifiedStreamDelta` | 供应商适配层已经产出 `text_delta`、`reasoning_delta` 和工具调用增量；在 Harness 调用层接通现成的正文回调 | 无新依赖；不能把增量直接当作已确认的最终回答 |
| `@ag-ui/core` 与现有主进程、预加载、渲染进程事件桥 | 用已有 `CUSTOM` 事件传递临时正文；保留现有正式回答的 `TEXT_MESSAGE_START/CONTENT/END` | 无新传输协议；临时正文的归类是本项目业务逻辑，需少量自定义事件处理 |
| `StreamController` | 继续缓存每轮完整正文，供工具轮、最终回复和模型历史使用 | 不能删掉；要解除的是“缓存完成前不让界面看见”的限制 |
| 现有过程卡、推理块、`XMarkdown` 与浏览器 `requestAnimationFrame` | 复用过程区和文字渲染；每绘制帧至多发布一次累计临时正文 | 不引入逐字动画库；长正文仍需验证渲染成本 |
| 已安装的 `@ant-design/x-markdown` 流式配置 | 使用其 `hasNextChunk`、`tail.component` 和可选 `enableAnimation`：组件负责把尾标放在最后一段可见文本后，自定义组件只负责视觉呼吸 | 无新依赖；内置尾标本身没有呼吸样式，且在末尾不是文本时可能不插入，仍由现有“生成中”状态承担持续反馈；新字淡入须验证长文性能 |

dsh 的“先显示当前步骤、整轮结束后归类”可作为行为参照，但其会话日志和前端投影架构与本项目不同，不直接移植模块。这里使用现有依赖和标准浏览器能力，不新建通用流式基础设施。

## 现状与需要改变的边界

`src/main/orchestrator/harness/harness-llm.ts` 已收到模型增量，但仅将推理增量上报；正文由 `src/main/orchestrator/harness/cyrene-harness.ts` 在整轮响应完成后写入 `StreamController`。有普通工具调用时，`tool-round.ts` 把全文发成 `progress_text`；否则 `cyrene-harness.ts` 把全文发成 `final_answer`。`adapter/event-mapper.ts` 把后者包装成一组连续的正式文本事件。前端 `AgentRunController.ts` 因此只在模型这一轮结束后才拿到正文，并在非聊天模式用最多 24 次、间隔 14 毫秒的本地渐显播放。

旧设计 `docs/design/2026-08-08-cyreneHarnessloopdesign.md` §7 明确选择先缓冲正式回答，防止模型尚未完成工作却先声称已完成。本方案改变运行期的可见策略，承认用户可能短暂看到后来被归入过程区或撤销的文字；通过显著的“生成中”状态、终态原子结算和不持久化临时正文控制风险。临时预览不能用于表示工具执行成功。

## 状态与事件设计

每轮模型请求使用已有 `roundId` 关联临时正文。Harness 新增两个内部事件：

- `candidate_text_delta { roundId, delta }`：模型产生经过现有过滤的可见正文时发送。没有可见正文不发送。
- `candidate_text_discard { roundId }`：已知这一轮文字不应作为过程或正式回答保留时发送，至少覆盖 `ask_user` 等排他交互。

适配器把它们映射为 `CUSTOM` 事件 `cyrene.candidate_text`，`value` 带 `roundId`、`action: "delta" | "discard"` 和仅在增量时存在的 `delta`。继续沿用桥层注入的 `runId`；渲染端先通过既有 `RunEventGate` 校验运行，再检查 `roundId`，丢弃旧轮次事件。新增事件只承载临时呈现，不改变现有 `progress_text`、`final_answer` 或正式文本事件的含义。

选择自定义事件而不提前发送 `TEXT_MESSAGE_*`：当前正式文本事件已经被前端用作提交判定，且桥层会对它执行 `<think>` 与时间前缀过滤。复用它传临时正文会把“预览”和“已确定的答复”混在一起，并需要重定义现有消费者。正文增量取自供应商流适配层现有 `<think>` 过滤之后；候选通道再复用 `src/main/chat-time-stream-filter.ts` 的时间前缀过滤器，避免先闪出系统时间。最终正式事件仍走原桥层，结算时以后者为权威文本。

前端每个运行只保留一个当前轮候选值：`{ roundId, text }`。它存放在渲染态消息的可选 `transientText` 字段，不写进共享的 `ChatMessage` 持久化类型。渲染时优先显示该字段；已有 `content` 继续仅代表正式正文。候选状态与 `responseStarted`、`streaming` 一同控制当前回答区的“生成中”外观。推理仍走 `REASONING_MESSAGE_*` 和现有过程卡，不与候选正文混写。

| 事件或结局 | 前端动作 | 持久化与播报 |
| --- | --- | --- |
| 当前轮正文增量 | 累计到 `transientText`，按绘制帧合并刷新回答区 | 不写正式正文、不启动早播语音 |
| 普通工具调用轮的 `cyrene.process_text` | 用权威全文生成过程消息；同一次消息补丁清空当前轮 `transientText`，避免重复或短暂双显 | 过程消息按现有检查点节奏落盘 |
| 无工具轮的正式文本事件 | 收齐权威正文并等待 `TEXT_MESSAGE_END`；若有候选预览，不再播放一次完整的本地渐显 | 尚不提交正式正文 |
| `RUN_FINISHED` 且成功、正文结束、非空 | 在同一次消息补丁中将权威正文写入 `content` 并清空 `transientText`；外观由“生成中”变为已完成 | 继续按现有终态检查点落盘；此后才允许早播语音完成 |
| `candidate_text_discard` | 清空对应轮次的预览，不生成过程消息 | 不落盘 |
| 取消、超时、运行错误或正式文本缺失 | 不提交正式回答；将尚未结算的可见候选文字作为“中断的过程片段”放入现有过程区，清空回答区；错误文案保持现有逻辑 | 沿用现有终态与过程快照；取消早播语音 |

正式答复与预览不一致时，以正式事件全文替换预览，不能简单追加，否则会重复文字。出现工具调用时，也以现有 `progress_text` 全文为准；若中途取消导致没有权威全文，才采用前端已看到的候选片段，并标识为中断而非工具结果。

## 显示节奏与恢复

临时正文在内存中逐增量累积，界面更新合并到下一次 `requestAnimationFrame`；工具、丢弃和终态事件到达时先冲刷或取消待绘制帧，再原子归类。不能人为按字符定时播放已收齐的文本。原有 `splitTextForReveal` 仅保留给无真实增量的非流式兜底；普通 Harness 增量路径不再使用它。

过程卡在运行时仍按现有规则展示推理和工具活动，结束后按现有规则折叠。候选正文显示在回答区，带本地化“生成中”提示；没有候选正文时不制造空回答气泡。工具轮归类后，下一轮重新开始一份候选正文，不复用上一轮文本。

### 末尾呼吸提示与新字淡入

用户看到的“停顿时最后一个字仍半透明地呼吸”属于呈现动效，不能据此判断模型是否仍在产生文字。本方案让已收到的正文立即进入排版，再用一个靠近最后可见字符的半透明尾标表示“本轮仍在生成”。尾标可做成细窄、接近字宽的标记，约每 1 秒在 35%～80% 不透明度之间缓慢往复；正文字符始终保持正常不透明度，避免把实际内容变成闪烁文本，也不影响复制和选择。新增正文到达时，尾标随最后一段文本移动；没有新增量的短暂停顿中，尾标仍继续呼吸，不额外补字、不伪造匀速输出。首次可见正文前继续使用已有运行指示，不显示孤立尾标。

复用 `XMarkdown` 的 `streaming={{ hasNextChunk: true, tail: { component: ... } }}` 在候选正文末尾注入尾标；当前 `ChatMessageList.tsx` 固定传入的 `completedMarkdownOptions` 只用于已完成消息。自定义尾标组件和少量样式只实现外观，标记设为辅助技术不可读，旁边保留可读的“生成中”状态。`enableAnimation` 可给新到文字做约 150～200 毫秒的淡入，但只在真实增量路径开启，先用长正文和复杂 Markdown 检查重排与性能；若成本明显，保留尾标而关闭新字淡入。尾标插入不了的末尾结构（例如代码块）继续显示“生成中”状态，不另写解析器修改文本末字。

收到工具调用并把候选正文归入过程区、收到正式答复并原地确认、排他交互丢弃，或运行取消、失败、超时时，尾标随候选态一次性消失；历史过程记录和正式回答均不带尾标。系统要求减少动态效果时，取消呼吸与淡入，保留静态且清晰的“生成中”文字。尾标仅反映界面仍处于活跃运行态，不能表示连接健康，也不能代替实际超时和错误提示。

临时正文不写入检查点，以免将未确认声明变成历史事实或产生逐增量写盘。页面刷新后，已显示但未归类的预览可能消失；既有运行接管与终态恢复行为保持不变。跨刷新重播正在生成的候选正文属于单独的运行流重连能力，不在本次范围内，验收时必须如实记录此限制。

## 施工顺序

### 1. 打通模型正文增量，但不改变最终语义

修改 `src/main/orchestrator/harness/harness-llm.ts`：在现有 `onReasoningDelta` 旁增加正文增量回调，复用 `streamChatWithSdk` 的 `text_delta`。修改 `cyrene-harness.ts`，为每轮绑定 `roundId`，用现有 `ChatTimeStreamPrefixFilter` 处理候选增量和流结束的尾部，再发出 `candidate_text_delta`。保留 `StreamController.bufferProgressContent`、`flushProgressBufferAsProgress`、`commitProgressBuffer` 和原有工具判定。非流式供应商兜底没有实时增量，保持原行为。排他交互在进入等待前发 `candidate_text_discard`。

修改 `harness/types.ts` 和 `harness/adapter/event-mapper.ts`，只新增上述两种临时事件映射。验证事件顺序：增量先于该轮的过程或正式结算，正式文本事件仍只有一套，取消后不再出现迟到增量。

### 2. 前端临时消息与原子归类

在 `src/renderer/react/features/chat/pages/chat-page-bridge.ts` 声明自定义事件载荷的类型；在 `src/renderer/react/features/chat/pages/run/AgentRunController.ts` 增加当前轮候选状态、逐帧合并和五种结算分支。最好把纯状态转移抽成同目录的小模块 `candidate-text.ts`，让控制器继续负责事件与检查点，不在其中叠加另一套文字解析器。

在 `src/renderer/react/features/chat/components/ChatMessageList.tsx` 的渲染态消息上增加可选 `transientText`，复用现有助手正文渲染器，增加本地化的“生成中”标识。候选正文开启 `XMarkdown` 的尾标配置，并以轻量组件和样式实现呼吸；已完成消息继续关闭流式配置，减少动态效果时关闭动画。正式 `content` 和持久层 `src/shared/chat-types.ts` 不加临时正文字段。过程区使用已有 `ProcessMessageRecord`；检查点仍从控制器的正式正文与过程记录构建。早播语音只接收确认后的正式正文。

### 3. 处理终态和兼容路径

核对主进程 `agui-bridge.ts` 的 `<think>` 过滤、时间前缀过滤和 `RUN_FINISHED` 延后发送顺序，确保候选增量与最终正文允许不同但最终结算唯一。旧版本事件、无正文增量、无工具聊天和非流式降级都保留现有行为。针对停止、接管与新 `runId`，取消上一运行尚未执行的绘制帧，旧轮次不得修改新消息。

### 4. 验收与文档同步

为 Harness 增量转发、事件映射和前端纯状态转移写针对性测试；更新 `AgentRunController` 全流程测试，覆盖“慢速多段正文→无工具最终回答”“正文→工具调用→过程区”“推理与正文交错”“排他用户询问丢弃正文”“非流式兜底”“取消/错误/超时”“最终全文与预览不同”“跨轮与跨运行迟到事件”。增加界面检查：无新字的停顿中尾标仍呼吸，新字到达后尾标跟随，工具归类和各终态后立即消失，减少动态效果时静态可读，代码块末尾仍有生成状态。确认未确认正文不进入检查点或语音队列，最终回复不重复、不短暂双显。

运行相关 `vitest` 测试、主进程与渲染进程类型检查，并在工作、代码、学习、无工具聊天、启用工具聊天各做一次实际界面检查。人工记录首段文字到达与首次绘制的时间，以及工具归类时是否出现跳动。同步更新 `docs/design/2026-08-08-cyreneHarnessloopdesign.md` §7 或追加一条指向本方案的现行决策说明，避免旧“正式回答绝不预览”的描述继续被当作当前实现规范。

## 验收标准与明确限制

1. 支持流式的工具型模式，首段可见正文到达后，下一个浏览器绘制机会即可出现在回答区；无需等待模型整轮结束。
2. 工具轮正文最终只在对应过程记录出现一次；无工具成功轮的正文最终只在正式回答出现一次。推理始终归过程区。
3. 未确认正文不会作为正式消息落盘或播报；取消、错误、超时和排他用户交互不会产生正式回答。
4. 不支持流式的供应商继续使用原有兜底显示；刷新页面后暂不保证恢复运行中的临时预览。
5. 这是一项有意改变的可见性取舍：模型可能先说出后来被纠正的内容。界面必须清楚标识其“生成中”状态；若产品不能接受这种短暂暴露，应继续沿用现有先确认再显示的策略。
6. 真实增量停顿时，尾部呼吸提示可持续反馈但不生成额外字符；工具归类或运行终结后不再闪动，减少动态效果的用户能看到等效的静态状态文字。
