# Cyrene 对话与右侧工作区：交接施工总计划

## 交付目标和分工

由一个实施 agent 按下面阶段顺序施工；用户转发每阶段指令和回报；本对话负责审查回报、纠偏并发下一阶段指令。每一阶段完成并提交证据后再进入下一阶段。不要把全部需求合成一次不透明的改动。

目标有三组：运行中消息真正可排队且不会丢；工具型对话的正文到达即在回答区预览，并在轮次结果确定后归类；会话工作区可选择外部程序打开，并在右侧浏览文件、预览文件和查看运行差异。推理继续留在过程区。停顿时的半透明呼吸尾标只是活跃状态动效，不伪造新文字。

详细行为和边界以以下三份专项设计为准：

- `docs/design/2026-09-15-message-queue-dsh-reference.md`
- `docs/design/2026-09-15-live-candidate-answer-construction-plan.md`
- `docs/design/2026-09-15-workspace-open-files-review-design.md`

专项设计与现有代码冲突时，先报告具体代码证据，再做最小调整；不得悄悄改变最终回答、运行快照或工具调用的权威语义。

## 动工前必须核对的现状

当前工作树已有大量未提交修改，包括 `ChatPage.tsx`、`AgentRunController.ts`、Harness 事件映射及共享类型等目标文件。先运行 `git status --short`、查看目标文件 `git diff` 和新建文档，标出哪些是既有改动。保留用户全部现有工作；不得执行 `git reset`、`git clean`，不得覆盖或手动编辑生成的 `dist`。现有改动可能已覆盖计划的部分内容，以当前源码为准重新确认。

现状定位：`ChatComposer.tsx` 使用的 `Sender` 在 `loading` 时抑制提交，导致运行中排队入口难以到达；`ChatPage.tsx` 的 `pendingQueueBySession` 在页面内存中，且完成回调先移出队首再异步派发。Harness 已收到模型正文增量，但工具型模式完成一轮后才向界面交付整段；`AgentRunController.ts` 再用 `splitTextForReveal` 本地分段播放。右侧已有运行后固定 `ReviewSnapshot`，尚缺文件树、文件预览和外部程序选择菜单。上述是核查起点，不是跳过代码验证的理由。

## 复用决定

| 现成能力 | 直接替代或复用范围 | 成本、限制与自定义边界 |
| --- | --- | --- |
| 已安装的 `@ant-design/x` `Sender` | 继续承担输入框、附件和基础键盘行为 | 无新依赖；需适配运行中提交与独立停止按钮，不能仅靠 `loading` 配置实现队列 |
| Cyrene 现有会话文件存储与运行桥 | 队列权威数据、派发、恢复及会话级运行守卫 | 无新数据库；需少量会话业务适配与幂等记录，不引入 dsh 整套事件日志 |
| 已有模型增量、`StreamController` 和 `@ag-ui/core` 自定义事件 | 传递临时正文并保留原工具归类及正式答复 | 不新增通用流式框架；`StreamController` 的权威缓存必须保留 |
| 已安装的 `@ant-design/x-markdown` `XMarkdown` | 候选正文渲染、尾标挂载、可选新字淡入 | 无新依赖；复杂长文需验证性能，动效可降级为静态生成状态 |
| 已安装的 `antd`、`shiki`、`diff` 和现有 `RightInspector`、`ReviewDiffContent` | 文件树、标签、代码预览与固定运行差异 | 仅新增工作区安全读取、外部程序目录及会话标签适配；不重写差异算法 |
| Electron 的 `shell.openPath` 与 dsh 的外部应用目录／探测规则 | 默认打开目录；Windows 外部应用选项可参考或适配 | 指定程序须主进程检测、按参数数组启动；若复制 dsh 的 MIT 源码保留其版权和许可；不移植依赖 dsh 会话插槽的整包 |

dsh 的队列、文件树和右侧标签依赖自己的会话事件、资源地址和插槽系统，不能整包直接接入。`ui-dockkit` 仅在确有拖拽、浮动和分屏需求时评估；当前文件树、预览和差异标签用现有面板与 `antd` 更小。专属于 Cyrene 的候选答复归类、会话派发和固定差异语义仍需少量自定义逻辑。

## 阶段一：修好运行中排队入口

先调查 `ChatComposer.tsx`、`ChatPage.tsx` 的实际按键和按钮路径以及所装 `Sender` 的提交行为。运行中输入可编辑，普通 Enter 和明确的排队按钮能把当前草稿加入当前会话队列；Shift+Enter 保持换行，停止按钮独立工作，输入法组合期间不误提交。附件要按入队时快照保存；切换会话后不能错投。此阶段可沿用现有页面队列，但界面只能称“已加入本页待发队列”，不能暗示已持久化。不要顺手实现“运行中插话”。

验收：用真实 `Sender` 交互测试覆盖 Enter、按钮、Shift+Enter、停止、输入法、附件、切换会话；运行一次针对性测试和主／渲染进程类型检查。回报实际输入事件是否触达 `queueCurrentDraft`，以及失败测试证据。阶段一独立验收后再做可靠性改造。

## 阶段二：会话级持久队列与安全派发

把队列权威状态移到现有会话存储；旧会话无队列字段视为空。每条保留稳定标识、内容、附件引用和入队顺序。主进程确认入队后再清空草稿；入队失败保留草稿并提示。删除、编辑和认领按标识处理竞争。未认领的条目不提前进入正式用户历史或模型上下文。

当前 `src/main/agui-bridge.ts` 已有 `SESSION_RUN_ACTIVE` 会话级运行守卫与接管结算逻辑，先复用并验证刷新场景，不再新建锁；`docs/internal-issue/2026-08-25-harness-parallel-scheduling-known-issues.md` 顶部修复状态也已标明完成。认领队首后先可靠写入用户消息，再启动运行，持久记录可恢复的认领状态；只有确认派发成功才从待发视图移走。失败则停住该会话并提示重试，不能先移除再 `void dispatchUserMessage`。同一稳定标识的重试只能产生一条用户消息。进程恰在写消息与启动运行之间退出时，恢复为可继续的未完成状态。

验收：连续三条顺序、首条派发失败、跨会话隔离、删除与认领竞态、停止当前运行、页面刷新、进程重启、重复请求、旧运行尚在时的新提交。测试真实存储和运行桥，确认每条至多一次进入历史和模型上下文。若旧会话模式、附件生命周期或运行恢复不满足设计，先报告差距和兼容方案。

## 阶段三：正式回答实时预览与呼吸尾标

保留 Harness 的权威全文缓存及原有最终答复／过程事件，只加按 `roundId`、`runId` 关联的临时正文增量和必要的丢弃事件。候选正文在回答区逐增量显示，下一绘制帧合并刷新，不人为按固定速率吐字；推理仍进过程区。普通工具调用出现后，以权威过程全文替换候选并一次性归入过程区；无工具且成功时，以权威正式全文原地提交，不重复播放。取消、错误、超时、排他交互不提交正式正文。预览不写共享消息正文、不作为正式历史落盘或提前播报。

渲染侧复用 `XMarkdown` 的流式尾标位置，尾标用轻微透明度呼吸提示仍在生成，实际字形保持正常不透明度；无障碍减少动效时改为静态状态。代码块等尾标无法插入的结构仍要有“生成中”状态。候选归类、丢弃和终态时立即清尾标。流式路径不再使用 `splitTextForReveal` 做假播放；非流式供应商保留兜底。

验收：多段正文无工具、正文后工具调用、多轮、推理交错、正文与权威全文不一致、停止／错误／超时、排他交互、非流式降级、迟到事件、长 Markdown 与代码块。检查过程与正式区无重复瞬显，首段真实增量不等整轮完成才可见；记录刷新时临时预览不能恢复的既定限制。同步更新旧 Harness 设计文档的现行决策指向。

## 阶段四：外部应用打开工作区

在会话标题或项目入口做截图所示双段按钮：主按钮以记住的方式打开本会话工作区目录，箭头仅显示本机可用程序。默认打开复用现有 `CHATS_OPEN_WORKSPACE`；外部程序列表可参考 dsh `packages/host/open-in-app/src/catalog.ts` 与 `resolver.ts` 的 Windows 探测。启动程序和目录都由主进程按当前会话重新核实；前端只传程序标识，不传任意命令。未安装程序不出现，启动失败可见；选择记忆用现有设置存储。先以 Windows 为验收平台。

验收：不同会话打开各自目录，已安装程序显示、未安装不显示，记住上次方式；无目录、路径失效和启动失败有明确反馈。指定程序启动不经命令解释器拼接用户输入。

## 阶段五：右侧文件树、文件预览与固定差异

扩展现有 `RightInspector` 为会话级标签：文件树、按会话和相对路径去重的当前文件预览、本次运行固定差异、计划。文件树只在展开时读取该层；主进程只读接口逐次校验会话工作区根目录、最终解析路径、符号链接、大小及条目上限。文本和代码优先，Markdown 可切换源码／渲染预览；不能把内部“预览形式”与外部应用打开菜单混淆。后续图片等格式按现有预览能力增量接入。面板支持宽度调整和窄窗布局。

差异继续使用现有 `ReviewSnapshot`，点击运行后文件在右侧打开固定快照标签，明确标注“本次差异”；文件树预览明确标注“当前文件”。当前磁盘文件改变不得改写旧运行快照。对话内逐工具差异继续保留。先实现可用的文件列表和定位，再根据现有组件能力提供上一处／下一处变更。运行中未完成的计划修改不得冒充已完成运行差异。

验收：目录按需加载、同名文件跨会话隔离、关闭和切换标签、文本／代码／Markdown 显示、越界与过大文件拒绝、符号链接、刷新、窄窗、磁盘后来修改与旧快照不变。右侧文件预览和固定差异能并存且标签语义清楚。

## 每阶段的交付和回传格式

实施 agent 每阶段只交付该阶段，不在未审查时开始下一阶段。回报须包含：①当前阶段与代码发现；②改动文件及关键行为；③具体测试命令、通过／失败数量和人工界面核查；④与专项设计不同之处及原因；⑤尚未解决的风险。只报告实际运行的检查，不声称未跑的检查通过。用户把原文回传本对话后，由本对话审查并发下一阶段指令。

常规验证使用 `npm test -- <相关测试文件>`，需要时运行 `npm run build:main`、`npm run build:preload`、`npm run build:renderer`；现有构建会改写 `dist`，实施前须说明并保护工作树中原有生成文件变更。若只需类型检查，应优先用对应 `tsc --noEmit` 配置并确认配置兼容。阶段完成前查看 `git diff --check` 和最终变更范围。不要把用户已有的其他未提交修改计入自己的交付。
